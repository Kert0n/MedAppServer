# MedApp Server

REST API для домашней аптечки: что есть в наличии и что пора принять. Аптечки бывают общими —
семья, соседи. Система приватна по замыслу: о человеке не хранится ничего, кроме идентификатора и
хеша ключа.

Репозиторий самостоятельный: своя сборка, свой CI, своя история. Он же — серверная часть курсовой
работы [MedApp](https://github.com/Kert0n/MedAppDocs); там зонтичный репозиторий, документы курсовой и
две другие части — Android-клиент и скраппер справочника Vidal, — подключённые подмодулями.
Работать с сервером можно отсюда, зонтик для этого не нужен.

Три вещи, вокруг которых он и построен:

- **Упаковка, а не «лекарство вообще».** Пачка не пополняется: докупил — завёл вторую. Пустая
  выбрасывается. Отсюда и всё остальное — приёмы списывают из пачки, а не из абстрактного запаса.
- **Бронь принадлежит человеку, а не серверу.** Заявка может превышать остаток, и это законное
  состояние: чью долю ужать, решает владелец. Сервер за него не решает.
- **Клиент уходит в офлайн и возвращается.** Съеденное и новая бронь приезжают одним запросом на
  упаковку, атомарно, с предъявленными версиями — чтобы между списанием и правкой брони не
  оставалось окна.

## Архитектура

Слои разговаривают строго вниз: контроллеры → прикладные сервисы → оркестраторы → сервисы
агрегатов → хранилища. Подробное описание — в [ARCHITECTURE.md](ARCHITECTURE.md), правила и то,
чем каждое закреплено — в
[ARCHITECTURE-RULES.md](src/test/kotlin/org/kert0n/medappserver/ARCHITECTURE-RULES.md).

Границы слоёв не на честном слове: их проверяют тесты по исходникам, и нарушение роняет сборку, а
не всплывает на ревью.

Проект следует принципу **Privacy by Design**:

- о человеке хранятся только идентификатор и хеш ключа — ни имени, ни почты, ни телефона;
- журнал приёмов в базу не попадает: он слишком персонален для таблицы;
- недоступное неотличимо от несуществующего: иначе по коду ответа перебором узнаётся чужое;
- production не пишет application- и access-логи; диагностическое логирование остаётся только
  в локальном `dev`.

## Модель данных

- **User** — идентификатор и хеш ключа, больше ничего.
- **MedKit** — аптечка-контейнер и публичный счётчик участников. Каждый membership — отдельная
  связь `(medKitId, userId)`; идентификаторы других участников наружу не выдаются. Все участники
  равноправны: ни владельца, ни ролей.
- **Drug** — **упаковка**, а не «лекарство вообще». Пополнения не бывает: докупил пачку — завёл
  вторую упаковку. Пустая выбрасывается.
- **Reservation** — бронь: заявка человека на часть упаковки. Может превышать остаток — сколько
  из неё оставить, решает владелец, а не сервер.
- **DrugTemplate** — справочник Vidal, только для чтения.

Единицы измерения и формы выпуска (`QuantityUnit`, `FormType`) общие для справочника и заведённых
руками упаковок: «шт» — одна единица на систему, а не две одинаково написанные строки.

## Аутентификация и регистрация

1. `POST /v1/auth/register` — регистрация: логин (UUID) и пароль придумывает клиент и присылает
   телом; требует секрет в заголовке `X-Registration-Token` (см. `registration.secret`). Повтор с
   занятым логином — 409: учётные данные клиент знает до отправки, и токен по ним подтверждает, что
   учётка своя. В проде пустой секрет не даёт приложению стартовать.
2. `POST /v1/auth/token` — выдача JWT по HTTP Basic.

Регистрация ограничена по адресу клиента (в кеше — хеши адресов). Ограничение частоты выдачи
токенов настраивается отдельно и выключено в профилях `mock-prod` и `prod` для тестирования.
JWT по умолчанию живёт 10 минут.

## Версии и предусловия

Команда, меняющая упаковку или картину броней, предъявляет версию увиденного состояния: полем тела,
а где тела нет — параметром запроса `version`. `ETag` и `If-Match` не используются: заголовок
один, а ответ упаковки несёт два независимых состояния — саму пачку и картину броней на ней.
Membership и аптечка версии не имеют: join/leave меняют одну связь. Их жизненный цикл и перенос
держат корень исключительно, а создание упаковки или брони — совместимо, чтобы штатная гонка с
удалением давала доменный отказ, а не ошибку внешнего ключа.

| ситуация | ответ |
|---|---|
| версия не прислана | 428 |
| прислан мусор | 400 |
| предъявлена и не совпала | 412 |
| ресурс недоступен или его нет | 404 |
| дубль брони, повторное вступление, занятый клиентский идентификатор (в том числе приём или синхронизация под тем же идентификатором с другим телом) | 409 |

Повторы приёма и синхронизации сервер узнаёт по идентификатору не дольше суток и только в памяти
процесса: при большом числе записей старые вытесняются раньше, рестарт забывает все. Дальше повтор
судится как новый запрос — 412, если версия ушла вперёд. Повтор после того, как
пачка кончилась и уничтожена, отвечает 404: упаковки больше нет.

## Эндпоинты

Полный контракт — в [open-api.yaml](open-api.yaml); ниже оглавление.

### Аутентификация

- `POST /v1/auth/register` — регистрация с придуманными клиентом логином и паролем
- `POST /v1/auth/token` — JWT по HTTP Basic

### Пользователь

- `GET /v1/users/me` — снимок всего, что видно вызывающему, одним ответом

### Аптечки и участники

- `GET /v1/med-kits` — свои аптечки со счётчиками
- `POST /v1/med-kits` — завести аптечку
- `GET /v1/med-kits/{medKitId}` — аптечка вместе с содержимым
- `DELETE /v1/med-kits/{medKitId}` — удалить, при желании с переносом содержимого
- `POST /v1/med-kits/{medKitId}/invitations` — ключ приглашения с ограниченным сроком
- `POST /v1/med-kit-memberships` — вступить по ключу
- `DELETE /v1/med-kit-memberships/{medKitId}` — выйти

### Упаковки

- `POST /v1/med-kits/{medKitId}/drugs` — завести упаковку в аптечке
- `GET /v1/drugs/{drugId}` — упаковка вместе с бронями на неё
- `PATCH /v1/drugs/{drugId}` — правка описания и исправление количества
- `DELETE /v1/drugs/{drugId}` — выбросить
- `PUT /v1/drugs/{drugId}/intakes/{intakeId}` — списать съеденное; повтор под тем же
  идентификатором второй раз не списывает
- `PUT /v1/med-kits/{targetMedKitId}/drugs/{drugId}` — перенести в другую аптечку
- `PUT /v1/drugs/{drugId}/sync/{syncId}` — синхронизация: съеденное и бронь одной транзакцией

### Брони

- `GET /v1/reservations` — свои брони по всем упаковкам
- `POST /v1/reservations` — завести бронь
- `GET /v1/reservations/{drugId}` — своя бронь на упаковку
- `PATCH /v1/reservations/{drugId}` — изменить
- `DELETE /v1/reservations/{drugId}` — отменить

### Справочник и словари

- `GET /v1/drug-templates` — поиск по названию, латинскому названию, веществу и производителю
- `GET /v1/drug-templates/{templateId}` — запись справочника
- `GET /v1/form-types` — формы выпуска
- `GET /v1/quantity-units` — единицы измерения

Формы выпуска принадлежат серверу: каталог содержит 17 распространённых базовых форм и
«другие» для редких видов. Подробные названия исходного каталога преобразуются при загрузке;
клиент получает только короткий словарь и преобразует внешние названия в его формы.

Список сверяется с контрактом тестом `ReadmeRoutesTest`: разойтись молча он не может.

## Схема базы данных

Схему описывают объекты `Table` в `src/main/kotlin/.../db/tables`, а
[db/schema.sql](db/schema.sql) из них **порождается** — это производная, а не второй источник.
Файл применяется при инициализации Postgres в compose, поэтому на чистой машине схема появляется
сама.

Ни миграций, ни `ALTER`: схема создаётся с нуля. Изменения схемы, включая удаление прежней
`med_kits.version`, требуют новой базы или пересоздания существующего volume. После правки таблиц
перегенерировать снимок в том же коммите, за этим следит `SchemaSnapshotTest`:

```bash
./gradlew test -DupdateSchema=true
```

## Ключи подписи JWT

**В Docker делать ничего не нужно.** Сборка образа сама запускает
`src/main/resources/certs/gen.sh`, а он идемпотентен: если пары нет — создаёт, если она уже лежит
в `src/main/resources/certs/` — не трогает. Так что положенные вручную ключи сохраняются, а на
чистом клоне ключ появится сам. Ни переменных, ни параметров.

Для запуска на хосте (`./gradlew bootRun`) тот же скрипт, один раз:

```bash
src/main/resources/certs/gen.sh
```

Ключи в git не попадают (`.gitignore`). Ротация только явно, через `--force`: она инвалидирует все
уже выданные токены.

## Запуск с Docker Compose

### Локальная разработка

Ничего настраивать не нужно: при запуске с профилем `dev` (из IDE или `./gradlew bootRun`) Spring
сам поднимает Postgres из [compose.dev.yaml](compose.dev.yaml) и подставляет параметры
подключения. Схема та же, что в проде.

### Прод-подобная проверка

`application-mock-prod.properties` — production-like конфигурация с заведомо ненастоящими
секретами. Она позволяет локально проверить API на настоящем PostgreSQL и без Caddy.

```bash
docker compose -f compose.mock-prod.yaml up -d --build
```

Порт снаружи 18080, чтобы стенд не конфликтовал с приложением, запущенным из IDE.

### Прод

Production запускается с цепочкой `mock-prod,prod`: первый профиль содержит все политики, а
`application-prod.properties` активируется последним и перекрывает только реальный
`registration.secret` и пароль БД. Файл находится вне git и входит в локально собранный образ.
Те же два секрета передаются контейнерам через Docker secrets; пароль Postgres в любом случае
нужен контейнеру БД отдельным файлом:

```bash
mkdir -p secrets
openssl rand -hex 32 | tr -d '\n' > secrets/postgres_password
openssl rand -hex 32 | tr -d '\n' > secrets/registration.secret
```

Значения в `secrets/` и в `application-prod.properties` должны совпадать: файлы секретов
перебивают профиль, но расхождение означало бы два разных пароля к одной базе.

Приложение читает `/run/secrets` через `configtree`: имя файла становится именем свойства, поэтому
секреты из файлов совпадают со значениями, упакованными в профиль, и обёртка над entrypoint не
нужна. RSA-пара генерируется локально через `src/main/resources/certs/gen.sh --force` и также
входит в образ; это сохраняет у владельца ключи для проверки уже выданных JWT.

#### Развёртывание на сервер

Образ собирается локально: в него входят `application-prod.properties` и RSA-пара из `certs/`,
которых нет в git. Исходники серверу не нужны — только то, что читает compose. `medapp` ниже —
хост из `~/.ssh/config`.

Перед передачей проверяется именно закрытый файл, который будет загружен. Проверка требует
18 фиксированных форм, хотя бы одного препарата, согласованных ссылок и data-only SQL:

```bash
awk -f db/validate-catalogue.awk db/form-vocabulary.tsv init-scripts/cleaned-init.sql
sha256sum init-scripts/cleaned-init.sql
./gradlew test queryPlanTest
```

```bash
# 1. Образ — под платформу сервера, а не своей машины: с Apple Silicon без --platform
#    соберётся arm64, и на x86_64-сервере он не запустится.
docker buildx build --platform linux/amd64 -t medapp-med-app-server:next --load .
docker save medapp-med-app-server:next | gzip -1 | ssh medapp 'gunzip | docker load'
# Прежний образ помечается до подмены: откат — это вернуть метку latest на него.
ssh medapp 'docker tag medapp-med-app-server:latest medapp-med-app-server:previous && \
  docker tag medapp-med-app-server:next medapp-med-app-server:latest'

# 2. Обновление действующего стека. Каталог medapp задаёт имя compose-проекта и образа.
#    Существующие Caddyfile, секреты и RSA-пара остаются на месте.
ssh medapp 'mkdir -p /opt/medapp'
rsync -rltpR compose.yaml db/schema.sql db/load-catalogue.sh \
  db/validate-catalogue.awk db/form-vocabulary.tsv db/catalogue-health.sh \
  init-scripts/cleaned-init.sql \
  medapp:/opt/medapp/
# 3. Проверка файла и запуск с новым томом — ниже.
```

На новом хосте дополнительно передаются `Caddyfile`, `secrets/postgres_password` и
`secrets/registration.secret`; права выставляются по следующему абзацу. При обновлении
действующего стека эти файлы не перезаписываются.

Права на секреты — `644` на файлах внутри каталога `700`, а не `600`. Compose без swarm
монтирует файл секрета как есть, с правами хоста, а читают его не от root: приложение —
пользователем `spring`, Postgres — после перехода на пользователя `postgres`. Файл `600`,
принадлежащий root, им недоступен; от посторонних на хосте секреты закрывает каталог.

Справочник грузится только в новый том. После проверки файла и передачи всех частей стека
остановить compose, удалить **только** том базы и запустить образ без сборки:

```bash
ssh medapp 'cd /opt/medapp && sha256sum init-scripts/cleaned-init.sql && \
  awk -f db/validate-catalogue.awk db/form-vocabulary.tsv init-scripts/cleaned-init.sql'
ssh medapp 'cd /opt/medapp && docker compose -f compose.yaml down && \
  docker volume rm medapp_postgres_data && docker compose -f compose.yaml up -d --no-build --wait'
```

Сумма на сервере должна совпасть с проверенной локально. Тома Caddy не трогать: в
`caddy_data` лежат TLS-сертификаты, и частый перевыпуск упирается в лимиты Let's Encrypt.
Проверка здоровья Postgres требует точный словарь и непустой каталог также после рестарта:
повторный старт после сбоя init-скрипта больше не маскирует пустую базу.

#### Проверка после развёртывания

```bash
# На сервере: справочник загружен при инициализации — в логе «load-catalogue: готово»,
# в таблице десятки тысяч строк, а не ноль.
docker logs medapp-postgres-1 2>&1 | grep load-catalogue
docker exec medapp-postgres-1 psql -U medapp -d medapp-server-db -tAc 'select count(*) from parsed_drugs'
docker exec medapp-postgres-1 psql -U medapp -d medapp-server-db -tAc 'select count(*) from form_types'

# Снаружи, из /opt/medapp: продовый секрет принимается, токен выдаётся, поиск непуст.
B=https://medapp.ru.net
curl -s $B/actuator/health                                   # "status":"UP"
LOGIN=$(cat /proc/sys/kernel/random/uuid); PASS=$(openssl rand -hex 24)
curl -s -o /dev/null -w '%{http_code}\n' -X POST $B/v1/auth/register \
  -H "X-Registration-Token: $(cat secrets/registration.secret)" \
  -H 'Content-Type: application/json' -d "{\"login\":\"$LOGIN\",\"password\":\"$PASS\"}"   # 201
TOKEN=$(curl -s -X POST $B/v1/auth/token -u "$LOGIN:$PASS" | sed -E 's/.*"accessToken":"([^"]+)".*/\1/')
curl -s -G $B/v1/drug-templates --data-urlencode 'query=аспирин' -H "Authorization: Bearer $TOKEN"
```

Проверочная учётка остаётся в базе — удаления пользователя в API нет. Она пуста и ничего не
несёт.

Наружу смотрит только Caddy: приложение и Postgres портов не публикуют — на этом же держится
доверие к `X-Forwarded-For`.

### Справочник препаратов

Загружается при инициализации Postgres, во всех трёх профилях. Порядок задан именами файлов в
`docker-entrypoint-initdb.d`:

1. `db/schema.sql` → `01-schema.sql` — схема приложения, она создаёт и таблицы справочника;
2. `db/load-catalogue.sh` → `02-load-catalogue.sh` — данные справочника, если дамп есть.

Дамп в git не попадает — это закрытые данные. Монтируется каталог `init-scripts` целиком, а не
файл: при отсутствии файла Docker создал бы на его месте каталог. В prod и mock-prod отсутствие
дампа или неверный словарь останавливают загрузку и делают Postgres нездоровым; dev может работать
без закрытого каталога.

Выгрузка скраппера в исходном виде для загрузки не годится: она несёт свои `CREATE TABLE` и
спорит со схемой приложения. Преобразовать в data-only можно `db/rewrite-catalogue-dump.py`;
загрузчик проверяет это сам и отказывается грузить необработанный дамп.

Отказ загрузчика обрывает инициализацию Postgres — но только первый старт: том уже помечен
созданным, и следующий запуск проходит мимо init-скриптов. Healthcheck проверяет каталог и на
повторном старте. Весь путь — схема, загрузчик, поиск — проверяется тестом:

```bash
./gradlew queryPlanTest
```

`CatalogueDumpTest` грузит настоящий дамп в контейнер теми же тремя монтированиями, что и
compose, и убеждается, что справочник непуст и находится поиском. Дампа в git нет, поэтому без
него проверка честно пропускается — в CI она не идёт и идти не может.

## Конфигурация

Три профиля, каждый со своим файлом:

| Профиль | Файл | Роль |
|---|---|---|
| `dev` | `application-dev.properties` | локальная работа, ослабленные сроки и лимиты |
| `mock-prod` | `application-mock-prod.properties` | все production-политики и локальные секреты-заглушки |
| `prod` | `application-prod.properties` | только два реальных секрета, вне git |

Прод запускается как `mock-prod,prod`: второй профиль имеет приоритет и заменяет обе заглушки.
`RegistrationSecret` дополнительно запрещает старт production с mock-значением.

Основные параметры:

```properties
# Срок действия JWT токена (в минутах)
authentication.termInMinutes=10
# Ограничивать ли число запросов на выдачу токена с одного адреса
authentication.throttle.enabled=false
# При включённом ограничении: число запросов и размер окна (в секундах)
authentication.throttle.maxAttempts=20
authentication.throttle.windowInSeconds=300
# Срок действия ключа на присоединение к аптечке (в минутах)
medkit.share.termInMinutes=15
# Секрет для регистрации (отбиваем залётных ботов)
registration.secret=your-secret-here
# База данных
spring.datasource.url=jdbc:postgresql://localhost:5432/medapp-server-db
# Период, в течение которого с одного адреса нельзя зарегистрироваться заново
registration.timeout.InSeconds=30
# Сколько регистраций с адреса до ограничения
registration.timeout.BanNumber=1
```

## Тестирование

```bash
# Весь набор: правила, сценарии, гонки, откаты, число запросов
./gradlew test

# Планы запросов на объёме — отдельным набором, поднимает фикстур на сорок тысяч строк
./gradlew queryPlanTest
```

Тесты идут против настоящего Postgres в Testcontainers, а не H2: поведение зависит от СУБД —
локаль для триграмм, `numeric`, планы запросов.

Ставить Postgres не нужно, но нужен запущенный Docker (или другой совместимый runtime — Podman,
Testcontainers Cloud): контейнер поднимается сам, один на весь набор, версии той же, что в
compose.

## Безопасность

- JWT, RSA-ключи для подписи, stateless-сессии.
- Валидация входных данных; величины едут строкой и проверяются образцом.
- Запросы параметризованные — их строит Exposed, конкатенации SQL в приложении нет.
- Доступ проверяет сам запрос: чужая строка не читается, а не «читается и отбрасывается».
- Упаковки и снимки броней защищены версиями; один запрос `MedKitStore` держит корни аптечек
  исключительно для membership/переноса и совместимо для создания содержимого, при нескольких
  корнях — в стабильном UUID-порядке.

## Что стережёт репозиторий

| | что проверяется | когда |
|---|---|---|
| тесты | набор целиком и планы запросов на объёме | на каждый PR и push в main |
| CodeQL | статический анализ: инъекции, утечки, небезопасные умолчания | на PR, на push и по понедельникам |
| граф зависимостей | дерево сборки подаётся в граф репозитория | на push в main |
| проверка зависимостей | PR не добавляет зависимость с известной уязвимостью | на каждый PR |
| dependabot | обновления зависимостей и самих actions | раз в неделю |
| оповещения об уязвимостях | уязвимость находят и в том, что стоит давно | как только она опубликована |

Последняя строка включена настройкой репозитория, а не файлом: `dependabot.yml` задаёт только
расписание обновлений, а оповещения об уязвимостях и автоматические security-PR — переключатели
в настройках. В диффе их не видно, поэтому они названы здесь.

Первая строка держит третью и четвёртую. Граф репозитория наполняется сам только там, где
зависимости видны прямо в манифесте; у Gradle они известны лишь после разрешения конфигураций,
и дерево надо подавать. Пока подачи не было, в графе стояли восемь записей — все восемь сами
actions, — и проверка на PR сравнивала пустой список с пустым.

Чего пока нет: проверки контрольных сумм зависимостей
(`gradle/verification-metadata.xml`). Файл на тысячи строк, который ломается от каждого
обновления — то есть от каждого PR dependabot; браться за него имеет смысл, когда станет видно,
сколько таких PR в неделю.

## Логирование

Логи выводятся только в консоль в соответствии с Privacy by Design:

- `DEBUG` для пакета приложения, `INFO` для Spring;
- на диск не сохраняются;
- не содержат идентификаторов, количеств и прочего, что раскрывало бы чужие данные.
